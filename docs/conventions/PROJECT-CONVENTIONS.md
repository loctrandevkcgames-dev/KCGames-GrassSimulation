# GrassSimulation Project Conventions

This document is the tool-neutral authority for repository workflows and
project-level ownership rules in the GrassSimulation Unity project (game
working title: Grass Route).

## 1. Specialized Conventions

- For C# code and generated output, follow [CODING-CONVENTIONS.md](CODING-CONVENTIONS.md).
- Before staging or creating commits, follow
  [COMMIT-CONVENTIONS.md](COMMIT-CONVENTIONS.md).
- For game design intent, numbers and scope, follow
  [Grass-Route-GDD.md](../Grass-Route-GDD.md). Code does not silently redefine
  design rules; raise a mismatch with the Project Owner.

## 2. Repository Layout and Ownership

| Path | Owner | Rule |
|---|---|---|
| `Assets/GrassSimulation/` | Game | All game code, scenes, shaders and game assets. Default home for new work. |
| `Assets/Settings/`, `ProjectSettings/` | Game | URP assets, build profiles, input and project settings. Change only for a stated need. |
| `Packages/manifest.json`, `packages-lock.json` | Game | Package dependencies. Commit both files together. |
| `Packages/com.laicasaane.encosy-tower*/` | EncosyTower (embedded) | Framework source. See Section 3. |
| `Plugins/` | EncosyTower (embedded) | Source Generator and BCL plugin workspaces. See Section 4. |
| `Assets/Samples/Encosy Tower/` | EncosyTower (imported) | Imported reference samples. Do not edit or build game features on top of them. |
| `docs/` | Project | Design documents and conventions. |
| `.claude/`, `CLAUDE.md` | Agents | Agent-only instructions and skills. |

- Game assemblies live under `Assets/GrassSimulation/GrassSimulation.<Module>/`
  with an `.asmdef` named `GrassSimulation.<Module>` and the same root
  namespace. Add a new module only when it has an independent responsibility
  or dependency boundary; otherwise extend an existing module.
- Game code may depend on EncosyTower. EncosyTower must never depend on game
  code.
- Game code does not use Unity Entities (ECS). It uses Burst and the Job System
  for data-parallel hot paths (CODING-CONVENTIONS Section 13.2). The Entities
  packages remain installed only for the embedded framework.
- Always commit an asset together with its `.meta` file. Never delete, recreate
  or regenerate a `.meta` file to resolve a problem; a new GUID breaks every
  reference to the asset.

## 3. Embedded EncosyTower Framework

- EncosyTower is embedded so that the game can use and, when needed, fix or
  extend it. The game is the product; the framework is not released from this
  repository.
- Change framework code only when a game task needs it. Prefer solving the need
  in game code first. Keep framework changes minimal and general, without
  game-specific types, names or assumptions.
- Never mix framework and game changes in one commit. Commit the framework
  change first under its `EncosyTower.<Module>` topic, then the game change that
  uses it.
- Do not bump `package.json` versions, edit `Samples~`, run
  `Dev Tools > Update Version`, or perform other release steps unless the Project
  Owner explicitly asks.
- Record framework changes in the framework's own
  `Packages/com.laicasaane.encosy-tower/CHANGELOG.md` only when the Project
  Owner asks for changelog maintenance.

## 4. Source Generators

- For all Source Generator work, use
  `Plugins/SourceGenerator/EncosyTower.SourceGen.slnx`.
- Do not use the root `KCGames-GrassSimulation.slnx` for Source Generator work.
- A generator change must refresh its shipped analyzer and generator artifacts
  in their mapped Unity package destinations, so that Unity compiles with the
  change. Commit the refreshed artifacts with the generator change they come from.
- See [Plugins/SourceGenerator/README.md](../../Plugins/SourceGenerator/README.md) for
  artifact destinations and generated-source inspection guidance.

## 5. Unity-Owned Files

- Root `.csproj` files and `KCGames-GrassSimulation.slnx` are generated by Unity
  and ignored by Git.
- Do not edit generated project files manually. Let Unity refresh their contents
  and project membership, then reload dependent tooling.
- Never run `dotnet build`, `dotnet restore`, `dotnet test`, `dotnet clean`,
  `dotnet format`, MSBuild, NuGet restore, or equivalent commands against
  Unity-generated `.csproj`, `.sln`, or `.slnx` files unless the Project Owner
  explicitly authorizes the exact command and target.
- Do not run untargeted .NET, MSBuild, or NuGet commands from the repository root
  when they could automatically select a Unity-generated project or solution.
- A general request to build, test, validate, or diagnose does not grant this
  permission. Use Unity-owned compilation and test workflows instead (Section 6).
- This restriction does not prohibit commands against tracked, standalone .NET
  workspaces such as `Plugins/SourceGenerator/EncosyTower.SourceGen.slnx`, but
  task-specific validation restrictions still apply.

## 6. Working with the Unity Editor

- When a Unity Editor has this project open, drive it through the Unity CLI as
  described in the `grass-unity-editor` agent skill
  (`.claude/skills/grass-unity-editor/`). Several Editors can run on this
  machine; always target this project explicitly.
- Never hand-edit `.unity`, `.prefab`, `.asset`, `.mat` or `.meta` YAML while the
  Editor is open. Make the change in the Editor and save it. If no Editor is
  available, state that the edit was made on disk.
- Save scenes and assets in the Editor before staging them; unsaved Editor state
  is not in Git.
- Unity compilation (`recompile`) and the Unity Test Runner (`run_tests` or
  `unity test`) are the authoritative build and test checks for Unity code.
- Do not change the Editor version (`ProjectSettings/ProjectVersion.txt`),
  upgrade packages, switch build targets or rebake lighting/navigation without
  Project Owner approval.

## 7. Editor UI Asset Ownership

These rules apply to Editor UI in both game and EncosyTower code. Game Editor
code reuses the EncosyTower Editor APIs named below rather than duplicating
them.

- Put each feature's UXML/USS in its `StyleSheets/` directory. Use a `<Feature>StyleSheetPaths` owner with
  a `ROOT` composed from the nearest shared root and explicit `UXML_PATH` / `USS_PATH` or qualified variants.
  Preserve `.meta` GUIDs when moving existing assets; update consumers and active task contracts together.
- Reuse `EncosyTower.Editor.EditorAPI.LoadAsset<T>` for required assets, `GetOrLoadAsset<T>(ref field, path)`
  for caches, and `LoadStyleSheet` / `GetOrLoadStyleSheet` for skin selection. Keep dark/light caches separate.
  Feature owners hold paths and caches; do not duplicate loading, validity or exceptions in new `*Assets` helpers.
  Direct optional asset probes remain valid when absence is an intended result.
- Cached Unity assets must reload when destroyed, not only when their managed reference is null. Required-asset
  failures retain the shared path-bearing diagnostic; do not silently render an empty Inspector.
- Search shared APIs before adding utilities or guards. Shared Editor asset guards belong to
  `EncosyTower.Editor.ThrowHelper`; type-specific invariants stay with their owner, such as
  `BuildProfileOrTarget.ThrowIfInvalid`. Do not broaden visibility or add helpers without actual reuse.

## 8. Validation Evidence

- Treat static searches, Roslyn semantic analysis, .NET builds and tests, Unity
  compilation and domain reload, Unity Test Runner results, Play Mode
  verification, and player builds as separate evidence.
- Each validation layer proves only its own result. Do not substitute one layer
  for another or claim a check that was not run. Entering Play Mode is not proof
  that gameplay works; follow the Play Mode verification loop in the Unity CLI
  skill.
- Follow task-specific validation restrictions. Report the exact checks and
  results, plus anything intentionally not run or left for the Project Owner.
